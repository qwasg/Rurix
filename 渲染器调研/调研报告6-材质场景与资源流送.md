## 结论摘要（TL;DR）

四条线各有一个"最小可行答案"，且 2022–2026 的工业证据高度收敛。**材质**：不要做通用材质图，先做"单层 principled BSDF 闭合 + 逐像素材质分类"——Substrate 的官方文档证明即使 Epic 也要为新项目默认选固定内存、速度可预期的 Blendable GBuffer，把完整的 slab 拓扑留给按平台降阶的 Adaptive 路径[^225^]；rurix 的第一版材质闭合应该只有 Substrate Slab 输入的一个子集（albedo/F0/roughness/normal/emissive），多层混合归入 P3+。**变体**：PSO 爆炸的解法已经从"录制回放"进化到"预测式预编译"——UE 5.2 引入的 PSO precaching 在加载期按材质×顶点工厂×mesh pass 预测变体并后台编译，Fortnite 一场比赛预编译约 3 万个 PSO、实用于其中约 1 万个[^245^]；rurix 从第一天就应该把"按声明预测变体、运行时编译即告警"写进管线纪律。**场景**：GPU 场景扁平化 + 部件级微实例化是 2025–2026 的确定性方向——Nanite Assemblies 把部件 cluster 直接编码进最终网格的层级而不复制几何，Witcher 4 技术演示里最大的树磁盘占用从 3.5GB 降到约 29MB、单视图流送内存从约 36MB 降到约 2.7MB[^215^][^17^]。**流送**：几何与纹理共用同一套"页式驻留 + 反馈驱动 + 每帧预算"栈——Nanite 128KB 页（root page 常驻、父页引用约 30% 顶点、多级流入需拓扑排序安装）[^14^][^16^]，叠加 UE 5.6 Fast Geometry Streaming 的预算化思想（每帧 AddToWorld/RemoveFromWorld/网格流送预算可调、异步物理状态创建销毁）[^66^]；压缩侧磁盘用 GDeflate/Zstd 超压缩容器、纹理由 KTX2/BasisU 承担传输格式，DirectStorage 1.1–1.4 已经把 GPU 直解压与围栏批同步做成标准件[^232^][^235^]。

### 1.2 清单的读法

四条线的收敛点出乎意料地一致：**"磁盘格式面向 GPU 直转码设计、驻留按页、请求由渲染反馈驱动、每帧工作量预算化"**。Nanite 几何页、SVT 纹理页、Fast Geometry Streaming 的帧预算、DirectStorage 的 GPU 解压、KTX2 的运行时转码，本质是同一套思想在不同资源类型上的实例化。rurix 的正确姿势不是分头实现四个系统，而是先建一个**通用页式流送运行时**（优先级队列 + 预算 + 转码 + staging），让几何页与纹理页成为它的两种资源类型——这也是本报告把"流送栈"画成一张同构图的原因。材质线相对独立，但它的变体治理（PSO 预测）与流送的预算化共享同一个调度运行时。

## 2. 逐项分析：问题、算法、实现代价与工程复杂度

### 2.1 材质系统——Substrate 的教训与 rurix 的"单层闭合"

**要解决的问题。** 材质系统的核心矛盾是表达力（美术想要的图）与性能预算（每像素字节数与光照求值次数）之间的张力。Substrate 给出的工业答案是"slabs of matter"：材质是 principled BSDF 的 slab，图上做混合（mix）与分层（layer）操作，且**表示本身是原理化的，因此可以按平台能力自动简化**[^225^]。但 Epic 自己的默认选择暴露了真相：新项目默认 Blendable GBuffer——固定内存足迹、速度可预期、与非 Substrate 路径性能持平；完整表达力的 Adaptive GBuffer 要按材质复杂度收每像素字节税、强制 DBuffer decal、且只支持本代主机与 SM6 级 PC[^225^]。配套的降阶手段是 parameter blending：多 slab 合并为单 slab 单次光照求值，官方例子把四 slab 分层材质从 108 字节/像素压到 28 字节/像素[^225^]。

**实现代价与 rurix 选型。** 完整 Substrate 式系统是百万行级投入，rurix 不应模仿其图，而应模仿其**决策结构**：(1) 材质数据模型 = 单层闭合，输入为 albedo/F0/roughness/anisotropy(可选)/normal/emissive 的子集，全部有明确定义域与默认值（Slab 输入表可直接当规范用）[^225^]；(2) 渲染路径只有一条"Blendable 等价物"——固定字节 GBuffer 或 visibility buffer 材质 ID（与报告 1 的逐像素材质分类衔接）；(3) 预留"拓扑字段"（coverage weight/第二 specular lobe 权重），P3+ 再开多层。这样做第一周就能跑，且未来升级路径清晰：Substrate 证明原理化参数化是降阶的前提——参数有物理单位与定义域，简化才是可自动化的[^225^]。学术长线上，神经外观（Zeltner 2024，支持分层联合效果）与 MetaLayer（元学习分层 BSDF）指明了"复杂材质神经网络化"的方向，但 2026 年它们仍属跟踪项而非落地项[^251^][^252^]。

### 2.2 着色器变体与 PSO——从录制回放到预测式预编译

**要解决的问题。** 现代显式 API 要求"着色器+全部渲染状态"烘成 PSO 才能绘制；首次遇到的新组合在渲染线程上现场编译，单次几毫秒到几十毫秒，乘以真实游戏里散布在每个新区域、新武器、新特效上的数百个组合，就是"跑着流畅但不停卡顿"的千刀万剐[^242^]。UE 的答案经历了三代：UE4 时代的手工录制 bundled cache（玩一遍游戏记录 PSO，随包发行，加载界面集中预热）；UE 5.1–5.2 起转向预测式 PSO precaching——组件 PostLoad 时遍历它可能被渲染的所有 mesh pass，把材质×顶点工厂×pass 的预测变体集交给后台任务异步编译，proxy 创建时可选择等待 PSO 就绪或退回默认材质[^245^][^243^]。Epic 官方数字：Fortnite 一场比赛预编译约 30,000 个 PSO、实际使用约 10,000 个，相对于百万级的全组合空间依然很小；Epic 自己已完全放弃录制式、只靠预测式[^245^][^244^]。主机平台则根本没有这个问题——单一 GPU 目标意味着着色器随包发行即最终代码，状态装配不产生重编译[^245^]。

**实现代价与 rurix 纪律。** 预测式预编译的工程量集中在"变体预测器"：给定材质与几何类型，枚举它会经过的 pass（深度、阴影、velocity、base）与对应 shader 排列。rurix 的模块比 UE 少得多，预测器反而好写——报告 1 的 mesh pass 是有限集合，材质闭合是单层（2.1），特性开关是显式列表。配套三条纪律全部有出处：**源头减量**（UE Project Settings 的 permutation reduction 可按项目需求关掉整类特性置换、最多砍约 50% 变体[^227^]）；**运行时编译即告警**（把"渲染线程上发生编译"打进日志并纳入 CI，Stray Spark 手册的目标就是让该告警归零[^242^]）；**加载预算化**（Fortnite 首载因 precache 延长约 15 秒、移动端设超时+优先级提升[^244^][^245^]——rurix 的加载界面同样要按"只等高优先级"分级）。Unity 6 的 PSO tracing/precooking（GraphicsStateCollection 录制+预热双模式）证明这套思路已是跨引擎共识[^247^]。鉴别课同样重要：PSO 卡顿"每个唯一状态只发生一次"，traversal 卡顿"每次过边界都复发"——清驱动着色器缓存后复发的是前者，两者修法完全不同，rurix 的流送（2.4/2.5）治的是后者[^242^]。

### 2.3 场景表达——GPU 场景扁平化与部件级微实例化

**要解决的问题。** 场景表达要同时服务两件事：渲染端的 GPU-driven 消费（实例表、变换、可见性全部在 GPU 上）与内容端的磁盘/流送经济性（重复结构不重复存储）。Nanite 的管线从 Load 阶段就把场景图与实例列表拍平到 GPU，应用改场景图时增量更新 GPU 场景[^16^]。2025–2026 年 Epic 把"重复高细节几何"的表达推进到部件级：Nanite Assemblies 允许一个 assembly 引用最多 65k 个部件实例（树枝、针叶），构建时把部件网格的 cluster 直接编码进最终网格的层级而不复制部件几何，运行时在 cluster 剔除沿层级 descent 的过程中现算部件实例的最终变换；磁盘与流送的节省是数量级的——Witcher 4 演示最大树木 UASSET 从 3.5GB 降至约 29MB，单棵树单视图流送内存从约 36MB 降至约 2.7MB，500k 棵百万三角形级树木同屏成为可能[^215^][^17^]。代价是剔除阶段少量性能税与明确限制：单层实例化（assembly 不能再套 assembly）、引用相同部件的不同 assembly 各自存一份部件数据、骨骼网格部件只能绑定姿势[^215^]。

**实现代价与 rurix 选型。** GPU 场景表（实例→变换→网格→材质的全 GPU 化）rurix 经报告 1 的 indirect 管线已具雏形，P2 要做的是把它正式化为 `scene` 模块的唯一事实来源。Assemblies 思想对 rurix 的适配点不在植被而在**一切重复结构**：建筑构件、管线、栏杆、岩石群。最小实现是"两级实例化"——实例表项可以是"网格"或"部件实例组"，后者多一次间接寻址与变换复合，全部发生在 cluster 剔除的 descent 里（报告 1 的 `culling.rs` 扩展点）；构建侧在 `mesh/cluster.rs` 的 DAG 构建后加一趟"部件簇内嵌"（把部件 cluster 的页引用挂进宿主层级而非复制数据）。限制照抄 Epic：单层、不跨 assembly 去重[^215^]。与报告 6 流送的接口自然成立——部件页与宿主页都是流送系统的页，请求照常由剔除反馈驱动。

### 2.4 几何流送——页式驻留、反馈驱动与预算化

**要解决的问题。** 流送的目标是让"当前帧可见 cut 所需的数据"驻留，其余留在磁盘。Nanite 的机制经过源码级确认：几何按空间局部性与 DAG 层级装进 **128KB GPU 页（磁盘上 256KB）**，每个网格的 root page（含层级顶层）随资源加载常驻、永远有可渲染的东西；LOD 选择阶段产生反馈——被选中但未驻留的 cluster 所在页进入请求队列；全局页池有界（UE 默认 StreamingPool 512MB，`r.Nanite.Streaming.StreamingPoolSize` 可调），LRU 驱逐，驱逐跑赢流送就出现 pop-in[^249^][^33^][^16^]。两个精妙细节值得照搬：其一，**父页引用**——cluster 顶点约 30% 可编码为对同页或父页数据的引用，这是 LZ 看不到的冗余（父页数据只在 GPU 页池里），代价是多级同时流入时流送器必须拓扑排序保证父先子后，引用顶点还要把位流解码重编码成当前簇格式[^14^]；其二，**磁盘格式为 GPU 直解压设计**，thecandidstartup 明确指出 PC 上用 DirectStorage 是设计预期[^16^]。

**实现代价与预算化。** rurix 的 `mesh/streaming.rs` 要补四件事：页池（固定槽位 + LRU）、请求队列（剔除反馈 + 优先级类目，源码里有 2 位 STREAMING_PRIORITY_CATEGORY 字段[^249^]）、转码/staging 上传（图外，报告 5 纪律）、以及**每帧预算**——UE 5.6 Fast Geometry Streaming 把预算化做成一等公民：每帧 AddToWorld/RemoveFromWorld/网格流送均可设预算，异步物理状态创建与销毁把 GameThread 从流送路径上解放，Incremental EndPlay 与统一的异步加载时间预算进一步摊平尖峰[^66^]。它是 Epic 与 CDPR 合治开放世界 traversal stutter 的产物，目标正是"加载更快且帧率恒定"[^219^][^118^]。rurix 没有 UE 的 GameThread 包袱，但"每帧 I/O 字节数、转码页数、staging 上传字节数"三个预算计数器必须从 P1 就存在——流送系统最常见的失败模式不是算法错，而是单帧工作量无界。

### 2.5 纹理流送与虚拟纹理——SVT 的机制与适用面

**要解决的问题。** 纹理工作集超过显存时，mip 级流送的粒度太粗（整张贴图逐 mip 驻留），虚拟纹理把它细化到页：UE 提供 Streaming VT（磁盘熟数据页式流入，适合 lightmap/UDIM/大贴图）与 Runtime VT（GPU 按需生成，适合地形混合、decal 合成）两条路径[^239^]。工程上的关键是 feedback pass：不在主 pass 里逐 fragment 写反馈（会把只读采样变成写放大），而是单独一趟降分辨率渲染，用与采样着色器相同的导数数学算出虚拟页索引与 mip，打包成紧凑位编码写入反馈缓冲，由驻留策略消费[^233^]。硬件稀疏纹理（Vulkan sparse residency / D3D12 tiled resources）把页表翻译做进硅里，但**只提供机制不提供策略**——装哪页、何时驱逐、反馈怎么产生，各引擎都自己实现[^233^]。

**实现代价与 rurix 选型。** rurix 已有 `virtual_texture.rs` 雏形，P3 的目标是补齐 SVT 闭环：feedback pass → 页请求队列（并入 2.4 的通用流送运行时）→ 页表更新（Vulkan 侧 `vkUpdateSparseImageMemoryBindings` 或软件页表）→ 采样侧页表寻址。但必须记住综述作者的清醒判断：**虚拟纹理只在"纹理数据远超显存"的窄场景是净收益**，多数实时负载下传统纹理+KTX2 压缩的性能与迭代速度更好[^233^]。rurix 的正确顺序是先把 KTX2 纹理管线与 mip 流送做扎实（2.6），SVT 留给确实有超大贴图/地形需求的内容出现时；RVT 则与报告 2 的 surface cache/radiance cache 思想同族（GPU 按需生成页），可作为 GI 缓存的存储介质在那时再评估。学术侧的印证：Zhang 等 2022 年的大城市纹理流送正是"GPU 反馈优先级 + 稀疏部分驻留图缓存"的组合[^250^]，体渲染的 residency octree 提供同构的驻留层级[^254^]。

### 2.6 压缩与 I/O 栈——GDeflate、Zstd 与 KTX2 的分工

**要解决的问题。** 流送栈的下半截是"字节怎么从磁盘到 GPU 可用格式"。DirectStorage 的版本谱系给出了 Windows 侧的标准答案：1.1 引入 GDeflate GPU 解压与自定义压缩队列；1.3 加入 `EnqueueRequests`（一批请求用单个 D3D12 围栏同步，可让纹理加载与 `UpdateTileMappings` 严格定序）与 `DSTORAGE_DESTINATION_MULTIPLE_SUBRESOURCES_RANGE`（直接向纹理指定 mip 区间写入）；1.4 预览再加 Zstd 支持与 Game Asset Conditioning Library 的 shuffle 变换[^232^][^235^]。纹理则有专门的一层：KTX2/Basis Universal 是**传输格式**——ETC1S 约 0.3–3bpp 高压缩中低质量、UASTC LDR 8bpp 近无损（ASTC 与 BC7 的公共子集+转码提示位），运行时快速转码到 BC1–7/ASTC/ETC2/PVRTC 等几乎一切 GPU 格式，并可再叠 RDO+Zstd 超压缩[^241^][^229^]。几何侧，CGF 2024 的端到端压缩 meshlet 渲染与 zeux 的簇压缩工作证明"压缩 meshlet 直接成为 GPU 消费格式"已可行（与报告 1 联动）[^8^][^45^]。

**实现代价与 rurix 分工。** 三层各就各位：**容器层**（包内）用 Zstd/GDeflate 超压缩——Vulkan/Linux 路径没有 DirectStorage，rurix 需自写等价物：异步读 + GDeflate 计算着色器解压（参考其公开的 HLSL 实现）或先 CPU Zstd 后 staging，1.3 的"批量请求单围栏"思想直接借用到 `rhi/command.rs`[^235^]；**纹理层**全面走 KTX2——rurix 已有 `block_compression.rs`/ktx2，P1 要补的是按平台选转码目标（桌面 BC7/BC6H，移动 ASTC）与 ETC1S/UASTC 的质量分档策略[^241^]；**几何层**沿用报告 1 的 cluster 量化位打包作为内存格式，磁盘层叠 GDeflate/Zstd，父页引用作为第三级冗余消除[^14^]。验证口径统一：解压后页与离线参考逐字节一致（转码确定性），以及每帧解压/上传时间计入预算。

## 5. 必须新增的数据结构、shader 阶段、资源布局与验证方法

**数据结构（CPU/构建侧）。** `PageRequest { resource_id, page_index, priority_cat(2bit), frame_requested }`；`PagePool { slots: FixedVec<128KB>, lru, residency_bitmap }`；`StreamingBudget { io_bytes, transcode_pages, upload_bytes }`（每帧重置，FGS 思想）[^66^]；`MaterialClosure { albedo, f0, roughness, normal_id, emissive, flags }`（单层，定长 32B）；`MaterialTable`（GPU 定长数组，材质 ID 索引）；`PartInstanceGroup { part_mesh, transforms_base, count }`（两级实例化）；`VariantPredictor` 的 `PassSet × VertexFactory × MaterialFlags → ShaderKey[]` 映射表[^243^]；`PageStreamingState { bulk_offset, bulk_size, uncompressed_size, deps_start, deps_num }`（直接对齐 Nanite 源码结构）[^249^]。

**shader 阶段。** 新增三个：(1) **转码/解压 compute**（GDeflate 解压 + 几何页位流重编码为内存格式，父页引用顶点在此解码重编码）[^14^][^232^]；(2) **VT feedback fragment/compute**（降分辨率，导数算页+mip，紧凑位编码写反馈）[^233^]；(3) **材质分类着色**（从 visibility buffer/GB 读材质 ID，查 MaterialTable 求值——与报告 1 的逐像素分类同一 pass）。修改一个：cluster 剔除 descent 增加"部件实例组"分支（变换复合 + 二级间接）。

**资源布局。** 磁盘：几何 = 页化二进制（root page 随资源头，其余页 256KB 磁盘块 + fixup 表 + 依赖表）[^249^]；纹理 = KTX2（ETC1S/UASTC 分档）[^241^]；容器 = Zstd/GDeflate 超压缩包。内存（GPU）：几何页池（固定 128KB 槽位阵列）、纹理物理页池 + 页表（SVT）、材质表（定长）、场景实例表（SoA：变换/网格 ID/材质 ID/部件组指针）。staging 环形缓冲（图外上传，报告 5 acquire 屏障接入）。

**验证方法。** 四层。**正确性**：转码确定性（解压页与离线参考逐字节一致）；父页引用边界用例（多级同帧流入的拓扑排序正确性）[^14^]。**性能**：三预算超支告警；页池水位与驱逐率；pop-in 计数（选中页未驻留的帧数）；PSO 运行时编译告警归零[^242^]。**卡顿分类回归**：录制"新区域首入"与"重复过边界"两条脚本路径，前者验证 PSO precache 覆盖，后者验证流送预算——两类卡顿必须分别归因，鉴别法照 Stray Spark 手册[^242^]。**内容对照**：选一个重复结构重的测试场景（Assemblies 类），对比微实例化前后的磁盘/流送占用，目标对齐 Epic 的数量级口径[^215^]。

## 6. 风险与缓解

**最大风险是"流送系统各自为政"**：几何流送、纹理流送、SVT、PSO 后台编译如果各写一套队列与预算，rurix 会收获四个都要调参的子系统。缓解就是 3 节的核心决策——通用页式流送运行时先行，资源类型注册接入；PSO 后台编译虽不经过页池，但共享同一个"每帧工作量预算"调度器。**其次是变体爆炸失控**：单层闭合与 permutation 削减只是纪律，不是机制——机制是"运行时编译即告警进 CI"，没有这条，特性增加会悄悄把 precache 覆盖率稀释掉（Stray Spark 把缓存收集列为发版流程常驻项而非一次性修复[^242^]）。

**Assemblies 的诱惑与限制**：微实例化的收益演示极具冲击力（3.5GB→29MB）[^215^]，但它本质是"构建侧去重 + 剔除侧间接"，对低频重复内容收益甚微，还带来单层限制与跨 assembly 不去重的坑[^215^]。rurix 应在 P2 用真实内容做一次 ROI 评审再决定推广范围。**虚拟纹理的适用面**是最后一个坑：综述作者明言 VT 只在纹理远超显存的窄场景成立[^233^]——P3 标注"按需"正是为此，不要在 P1 顺手把 SVT 做了，它的页表/反馈/采样三件套会拖住流送运行时的稳定化。最后，**DirectStorage 是 Windows 专属**：Vulkan/Linux 路径的 GDeflate GPU 解压需要自维护（可参考其公开 shader），P1 的压缩栈验收必须在双平台上分别跑过，避免"Windows 很快、Linux 回退 CPU 解压拖爆预算"的分裂体验[^232^]。
