## 1. M29 `g8.p0.m29.shader_permutation`（host/compile 门）

### 1.1 实现方案

**新增模块 `src/rurixc/src/permutation.rs`**（纯 host、safe），四个子面：

1. **域声明语法**（attribute 形态，沿 `#[numthreads]`/`#[payload]` 既有 attr 机械）——附着于着色入口函数：

```text
#[permutation(axis(FOG, bool))]
#[permutation(axis(QUALITY, enum(low, med, high)))]
#[permutation(axis(LIGHTS, int(0, 4)))]          // 闭区间整数枚举
#[permutation(forbid(FOG = true, QUALITY = low))] // 禁组合 = 等式合取
#[permutation(budget(5))]                         // 声明预算上限
fragment fn fs_main(...) -> ... { ... }
```

   - axis 三类值域（RFC §4.3 冻结面）：`bool` / 整数枚举 / identifier 枚举；域 = entry 级（与 reflection v1 per-entry 的 `permutation_domain_digest`/`variant_key` 字段一一对应，不引入跨 entry 命名域）。
   - **约束子集第一期冻结为"禁组合等式合取表"**（每条 `forbid(...)` 裁掉匹配全部等式的组合）。这是 RFC"无副作用编译期布尔式"的封闭子集，机器可求值、可加性演进（未来放开 `!`/`&&`/`||` 走 spec 加性修订）；引用 profile capability 的约束留 M32 合入后加性接线。
   - 解析落 `iface_extract.rs` 同风格的 attr 提取（`parse_numthreads` 先例）；合法性校验（重名 axis、空值域、forbid 引用未知 axis/未知值、budget 非正）→ 编译期确定性拒。

2. **规范化与求解**：axis 按名字节序排序 → 笛卡尔枚举（`enumerated`）→ 逐 forbid 行裁剪（`pruned`）→ 余集 = `emitted`；恒等式 `enumerated == pruned + emitted` 是结构保证也是报告断言。防爆炸：枚举前先算 `∏|axis|`，超 budget 直接硬失败（不物化组合表）。

3. **canonical key**：
   - 二进制形态：`"rurix.permutation-key.v1\0"` + 按 axis 名字节序的 `(name, type_tag u32, value 规范编码)` 序列（沿 RXS-0305 CanonW 律：u32 LE + 长度前缀字符串）；
   - 展示/`variant_key` 字符串形态：`FOG=false;QUALITY=high`（排序后拼接，进 reflection `variant_key` 字段与 golden 比对）；
   - `permutation_domain_digest = SHA-256("rurix.permutation-domain.v1\0" || canonical_domain_bytes)`（非空域真值化；**空域恒既有常量** `rurix.permutation-domain-empty.v1` —— RXS-0304 空编码 0 漂移）。

4. **CLI 与报告**：`rurixc <file.rx> --emit=permutations [-o report.json] [--permutation-budget=N]`（CLI 覆盖 attr 声明的 budget，供 RED 腿）；报告 JSON（确定性、无路径/时间戳，沿 reflection JSON 纪律）含：per-entry `{domain_digest, axes[], enumerated, pruned, emitted, keys[], axis_contribution[]}`；超预算 → 非零退出 + axis contribution report 仍输出到 stderr/JSON。另支持 `--permutation-select=KEY`：校验 KEY ∈ 合法集（缺 variant = 确定性错误，禁"最接近"回退），选中后填 reflection `variant_key`（`pipeline_key` preimage 已含该字段与 domain digest，自动分裂——M31 既有接缝，零改动）。

**与既有面的接缝**：`reflection.rs` 只改两处——`permutation_domain_digest`/`variant_key` 从恒空编码改为"有域时真值化"（RXS-0304 修订行授权，见 1.2）；`driver.rs` 加 emit mode 分支（`"permutations"` 进白名单）。第一期**不做 per-variant body specialization codegen**（判据不要求；specialization 语义由 M32 的 capability 裁剪腿承载，spec 条款诚实注明归后续加性）。

## 2. M32 `g8.p0.m32.capability_profile`（host/compile 门）

### 2.1 实现方案

**新增模块 `src/rurixc/src/capability_check.rs`**（沿 `shared_check.rs`/`views_check.rs` 的 MIR/HIR 遍历风格），五个子面：

1. **capability ID 闭集**（编译器内 enum + 冻结字符串字面，spec 条款列全）：`rt.pipeline` / `rt.sbt_user_data` / `rt.any_hit` / `rt.intersection.procedural` / `rt.callable` / `rt.ray_query` / `mesh.task` / `sync.timeline_semaphore` / `queue.dedicated_transfer` / `queue.dedicated_compute`（RFC §4.5.1"至少覆盖"清单 + 加 `rt.ray_query` 以支撑当前树上唯一可构造的 fallback fixture——RayQuery compute 自 G7 全链在树）。backend extension 名不作 ID（RFC 逐字）。
2. **`#[requires("capability.id", ...)]` 语法**：fn 级 attr，字符串字面量列表；未知 ID → 编译期拒。
3. **隐式推导 + 调用图并集**：intrinsic 映射（`trace_ray`→`rt.pipeline`、`RayQuery`/`ray_query_initialize`→`rt.ray_query`、`report_intersection`→`rt.intersection.procedural`、`execute_callable`→`rt.callable`、`ignore_intersection`→`rt.any_hit`）、stage 映射（raygen/miss/chit→`rt.pipeline`，anyhit→`rt.any_hit`，intersection→`rt.intersection.procedural`，callable→`rt.callable`，task→`mesh.task`）、形参类型映射（`#[shader_record]`→`rt.sbt_user_data`，`AccelStruct` compute 签名→`rt.ray_query`）。有效 requirement = 显式 ∪ 隐式 ∪ 全部可达 callee 并集；device 函数无函数指针/间接调用，直调可达图静态可算（借 `mir_build` device 根收集 + typeck call facts），泛型着色函数不产 entry（与 M31 口径一致）。诊断消息携带**缺失 ID + 首个引入它的可达 callee**（RFC 判据形态逐字）。
4. **profile 声明**：构建 manifest 侧 JSON 文件，CLI `--profile <path.json>`；schema：`{name, version, required[], optional[], forbidden[], fallbacks: {logical_entry: fallback_entry}}`；`selected_profile_digest = SHA-256("rurix.profile.v1\0" || canonical_profile_bytes)`（canonical 律沿 RXS-0305；**无 `--profile` 恒既有 `rurix.profile-none.v1` 常量**，0 漂移）。不从开发机自动生成（RFC 逐字）。
5. **判定与 fallback 选择**：entry 有效集 ⊆（required ∪ optional）且 ∩ forbidden = ∅ → 合法；缺 required → 若 profile fallbacks 有映射且 fallback entry 接口契约兼容（比较两 entry 的 `io`/`resources`/`push_constants`/`execution_modes` 结构相等——reflection 内部函数，不加产物字段）→ **选中 fallback，主 variant 不发射**（"只生成允许的 specialization"字面）；无映射 → `capability.missing_required` RED；命中 forbidden → `capability.forbidden_used` RED；映射不兼容 → `capability.fallback_incompatible` RED。选择结果落 `--emit=capabilities` 报告 JSON（selection manifest：logical entry → 实际发射 entry + 各 entry 有效 requirement 集）。运行期 `capability.runtime_snapshot_mismatch` = rurix-rt 库层 typed Err（镜像 RX6029/6030 口径不占 RX 码），M32 门只落 host 原语（`verify_profile_snapshot` 纯函数，M50/M89 device 腿消费）。

**接缝**：`reflection.rs` 两处真值化——`required_capabilities`（排序 ID 表）与 `selected_profile_digest`（RXS-0304 修订行）；`driver.rs` 加 `--profile`/`--emit=capabilities`；codegen 根收集按 selection 过滤（`--profile` 未给时行为 0-byte）。

## 3. M30 `g8.p0.m30.pso_cache`（driver/device 门）

### 3.1 实现方案

**新增模块 `src/rurix-rt/src/pso_cache.rs`** + `vk.rs` FFI 追加段 + **新 harness `src/rurix-rt/src/bin/vk_pso_cache.rs`**（沿 `vk_rt.rs`/`vk_mesh.rs` 体例）。四个子面：

1. **PSO key 定义**（纯 host、可单测）：
   `pso_key = SHA-256("rurix.pso-key.v1\0" || preimage)`，preimage 规范编码（CanonW 律）依次含：pipeline 种类 tag（0=compute/1=graphics/2=rt）、每 stage 的 SPIR-V blob SHA-256（artifact digest）、`interface_hash`、`selected_profile_digest`、`permutation variant_key`、固定功能状态规范编码（graphics：attachment format/blend/depth/顶点布局；compute：空；rt：group 拓扑摘要）、compiler/edition/target。**device identity 不入 pso_key**（跨机 key 集合 golden 可比对），单独构成 **cache artifact identity**（RFC §4.1.4"driver query 值不影响 interface hash，但影响 pipeline cache device key"的落地拆分）。
2. **固定场景 collector**：`PsoCollector` 消费固定 workload 描述表（fixture 集 = 既有确定性 SPIR-V：`vk_saxpy`/`vk_fill`/`vk_atomics_w1` 三 compute + `vk_tri_vs/fs` 一 graphics + `emit_raygen/miss/closesthit_min` 一 rt，共 5 条 pipeline），host 侧产 key 集合；golden `tests/pso/pso_keys.golden.json` checked-in。
3. **持久化 store（磁盘格式，fail-closed）**：单文件 `<dir>/rurix_pso_cache.bin`：header = magic `"RXPSOC\x01"` + `schema_version u32` + device identity 段（`pipelineCacheUUID[16]` + vendorID + deviceID + driverVersion，全部实测自 `VkPhysicalDeviceProperties`）+ key-set digest + 分支 tag（binary/cache）；payload = 分支数据。**装载核验顺序**：magic/version → device identity 逐字段 → key-set digest；任一不符 = 丢弃 + 全量重建 + evidence 记 `rebuild_reason`，绝不部分命中。解析层纯 safe Rust（长度前置校验）。
4. **双分支 + compile-stall 计数器**：
   - **binary 分支**（`VK_KHR_pipeline_binary` 在位时**必须**走）：cold run 逐 pipeline 创建（带 `VK_PIPELINE_CREATE_2_CAPTURE_DATA_BIT_KHR`）→ `vkGetPipelineKeyKHR` + `vkCreatePipelineBinariesKHR`（from pipeline）+ `vkGetPipelineBinaryDataKHR` 落盘（per-pso_key blob）；warm run（**全新进程**）逐 key 从 store 重建 binaries → `VkPipelineBinaryInfoKHR` 链入 create → 断言零编译。
   - **fallback 分支**（扩展缺位）：`vkCreatePipelineCache(initialData)` / `vkGetPipelineCacheData` 整 blob 持久化；evidence 明记 `pipeline_binary_capability=false`。
   - **stall 计数器**（两分支同一定义，语义冻结进 spec）：warm run 全部 create 带 `VK_PIPELINE_CREATE_FAIL_ON_PIPELINE_COMPILE_REQUIRED_BIT`（`pipelineCreationCacheControl`，1.3 核心可选特性，实测协商），返回 `VK_PIPELINE_COMPILE_REQUIRED` 即 `runtime_compile_stalls += 1`；cold run 记 `precache_build_count`。计数器是 `PsoCacheManager` 的公开字段，进 evidence。
   - **FFI 追加**（vk.rs 类型/fn 指针 append 段）：`vkCreatePipelineCache/vkGetPipelineCacheData/vkDestroyPipelineCache` + `VK_KHR_pipeline_binary` 五符号 + `VkPipelineBinaryInfoKHR`/`VkPipelineCreateFlags2CreateInfoKHR` 等 repr(C) 结构。unsafe 归 U27/U31 既有 vk FFI 边界**扩注**；磁盘 blob 为不可信输入但解析在 safe 层完成——若评审认定"外部 blob 喂 `vkCreatePipelineCache`"构成新审计边界，才顺位领 U44。

harness 三模式：`--cold <dir>` / `--warm <dir>` / `--tamper <schema|version|driver_uuid|keyset>`，各自独立进程（"全新进程 warm run"判据字面），输出 JSON 供 smoke 消费。

## 4. M85 `g8.p0.m85.shader_manifest_ddc`（host 门，仅 `--phase g8.2` 腿）

### 4.1 实现方案

**新增模块 `src/rurixc/src/manifest.rs`**（纯 host、safe）+ driver 工具模式：

1. **manifest v1 模型**：`schema = "rurix.shader-manifest.v1"`；两段记录：
   - shader 记录：`{entry, stage, interface_hash, source_digest, selected_profile_digest, permutation_domain_digest, variant_key, pipeline_key}`（全部字段来自 reflection v1 产物，零第二事实源——P-11）；记录键 = `pipeline_key`；
   - PSO 记录：`{pso_key, kind_tag, stage_digests[], fixed_function_digest}`（来自 M30 collector 输出）；记录键 = `pso_key`。
   canonical bytes 沿 RXS-0305 律（版本前缀 + 记录按键字节序排序），`manifest_digest = SHA-256("rurix.shader-manifest.v1\0" || canonical)`——该 digest 即 g8.3 腿进 DDC key 的组成项（字段位本期冻结，DDC put/get 归资产波）。
2. **canonical merge / dedup / 冲突**：输入 N 份 per-unit manifest JSON → 按键归并：同键同 payload → 恰好一条（dedup）；同键异 payload → **冲突 fail-closed**（typed Err，列出键与相异字段）；输出排序后 merged manifest + digest。coverage 核验：输入侧声明的 entry/variant/PSO 全集必须在 merged 中恰好各现一次（缺 = coverage 缺口 RED）。
3. **CLI**：`rurixc --merge-manifests -o merged.json a.json b.json ...`（driver 工具模式，不走编译管线；per-unit manifest 由 `--emit=reflection` 产物 + `--emit=permutations` 报告 + M30 collector JSON 经同一模块的 `from_parts` 装配——smoke 里由脚本按固定 fixture 驱动 rurixc 产出，不手写）。
4. **phase 纪律**：smoke `--phase g8.2` 只跑 merge/dedup/coverage 腿并写 `phase_g8_2_pass`；`phase_g8_3_pass` 字段在 schema 中必填、g8.2 期恒 `false`（诚实登记，g8.3 腿由资产波脚本同一 `--gate` 不同 `--phase` 补真；任一腿不代另一腿充绿——判据字面）。

## 5. M50 `g8.p0.m50.rt_pipeline_incremental`（device 门）

最重的一门。判据六项（①多 hit group golden hit-id ②SBT 用户数据逐字节 readback ③stack `configured >= required` ④分库≡单体逐像素 ⑤冻结子集逐项 RED-GREEN ⑥validation=0）要求**同一场景一次运行**同时成立。当前树上 RT 阶段是固定最小模块，故 M50 = 语言/编译面 + 运行时面两大块，建议拆 3 个 commit（spec → 编译器 → runtime/device）或 2 个 PR 同门收口。

### 5.1 实现方案

**A. 编译器面（rurixc）**

1. **`#[shader_record] record: &R` 类型面**（`shader_stages.rs` 扩，沿 `#[payload]` 家族机械）：仅六 RT 阶段签名形参合法（他处 → RX3013 扩类别，位置纪律先例）；`R` 闭集 = 标量/定长向量/定长数组/由其组成的 struct，禁资源句柄/裸指针/引用字段/runtime array/递归 → RX3012 扩类别（RT 数据契约家族先例，**零新码**）。record 布局律冻结：顺序布局，标量沿 push-constant 律（i64/u64 8 对齐、余 4），`vecN<T>` 对齐 = 分量对齐×(N==3?4:N)，数组元素紧排——`record_schema_hash = SHA-256("rurix.shader-record.v1\0" || canonical_fields)`。
2. **hit group 声明语法**（最小冻结面）：`#[hit_group(NAME)]` 附着 closesthit/anyhit/intersection 入口，同名聚为一组；组形态校验按 RFC §4.1.1 冻结表（triangles = chit 必选 + anyhit 可选；procedural = intersection+chit 必选 + anyhit 可选；triangles 带 intersection / procedural 缺 intersection → 编译期拒，RX3017 扩类别"RT 入口标注契约"）。raygen 恰一个、miss ≥1 按声明序、callable 按声明序、group 按首现序定 `group_index`。**pipeline manifest 域 = 单编译单元**（RXS-0244 修订后的"manifest 全域"字面）。
3. **manifest 产物**：`--emit=rt-manifest`（独立 JSON `rurix.rt-pipeline-manifest.v1`：raygen/miss[]/hit_groups[]/callables[]/单一 payload schema hash/逐组 attr+record schema hash/required capabilities/recursion=1/interface hash）。**不动 reflection v1 文档级闭集**；entry 级 `rt_payloads/rt_hit_attributes/rt_callable_data/shader_records/rt_group_membership` 空表真值化已被 RXS-0304 预授权（"M50 落地时按同一序列化规则填充"），`enumerable_stage` 解除 RT 不可枚举诚实边界（spec 修订行）。
4. **RT 六执行模型真实体 lowering**（`mir_build.rs` RT 根收集 + `vulkan_codegen.rs` 主体，最大工程量）：新增 RT 存储类变量（`(Incoming)RayPayloadKHR`/`HitAttributeKHR`/`(Incoming)CallableDataKHR`/`ShaderRecordBufferKHR` block）；`#[shader_record]` → ShaderRecordBufferKHR block（布局与 packer 同律）；`trace_ray` 从固定见证升真实调用点（SBT offset/stride/miss **仍编译期恒定**——寻址由 TLAS instance 的 `instanceShaderBindingTableRecordOffset` 装配期承载，RXS-0245 修订行字面）；`report_intersection(t, attr)`→`OpReportIntersectionKHR`；`ignore_intersection() -> !`→`OpIgnoreIntersectionKHR` 终结（仅 anyhit，他处编译期拒）；`execute_callable(INDEX, data)`（INDEX 须编译期常量且 < manifest callable 数 → typeck 证明在域）；raygen 输出走既有 storage buffer/image 面 + launch id builtin（RXS-0245 RT builtins 面扩 launch_id/launch_size，若既有面未含则同 PR 加性）。body 表达力复用 compute 路已有 lowering（SSA/place 投影 G7.4 已扩向量分量），首期语料只用已验证子集。
5. **capability 接缝**：六阶段隐式 requirement（M32 映射表）；缺能力 RED 腿即 M32 原语复用。

**B. 运行时面（rurix-rt vk.rs + 新 harness）**

1. **`plan_sbt_v2`**（纯 host 新函数 + 单测；既有 `plan_sbt`/RXS-0248 golden **0-byte 恒跑**，RFC §4.1.6 授权"多 record 铺设作为新增纯 host 单测"）：四 region（raygen/miss/hit/callable），region stride = `align_up(handle_size + region 内最大 record 尺寸, handle_alignment)`，region base 对齐 `base_alignment`；record 数据紧随 handle（ShaderRecordBufferKHR 起址律与 codegen 同律冻结）。
2. **record packer**（host）：输入 = record schema（来自 rt-manifest/reflection）+ 原始字段值，输出 bytes；核验 schema_hash 与目标 group 精确匹配、总尺寸/对齐律；**禁 repr(C) memcpy 充当契约**（packer 是唯一合法编码入口，RED 腿含 hash 错配拒）。
3. **`run_rt_pipeline_offscreen(desc)`**（新入口；既有 `run_ray_tracing_offscreen` 0-byte 保留供步骤 66/67 恒跑）：
   - `RtPipelineDesc { raygen, miss[], hit_groups[]{kind, chit, anyhit?, intersection?}, callables[], records{per-region bytes}, scene, stack_override? }`；
   - stages/groups 数组按 manifest 序构造 `VkRayTracingShaderGroupCreateInfoKHR`（TRIANGLES_HIT_GROUP / PROCEDURAL_HIT_GROUP / GENERAL）；
   - **AS 建面复用 `VkAsManager` 单所有者**（G7 纪律，禁第二套 BVH 所有者）：加性扩 per-instance `instanceShaderBindingTableRecordOffset`（manifest 的 `(instance,geometry)→group/record` 静态映射；越界/漏映射/不一致 → 装配期 typed Err）；procedural 腿为 manager 加 AABB geometry 建 BLAS 支（加性）；
   - **stack sizing**：`vkGetRayTracingShaderGroupStackSizeKHR` 逐组逐 shader 类查询 → 保守公式（版本号冻结进 evidence）：`raygen + max(chit_max, miss_max, intersection_max + anyhit_max) × 1 + callable_max`（递归 1、callable 深度 1、禁嵌套）→ pipeline 带 `VK_DYNAMIC_STATE_RAY_TRACING_PIPELINE_STACK_SIZE_KHR` → `vkCmdSetRayTracingPipelineStackSizeKHR(configured)`；trace 前 host 复核 `configured >= computed`（`stack_override` 人为缩小 → 确定性拒 = RED 腿，不触 UB）；
   - **pipeline library**：扩展协商追加 `VK_KHR_pipeline_library`；每库 = 完整 group/callable 子集，`VK_PIPELINE_CREATE_LIBRARY_BIT_KHR` + `VkRayTracingPipelineInterfaceCreateInfoKHR{maxPayloadSize, maxAttributeSize}`（取自 manifest schema 尺寸）；final link 按主 manifest 声明序 `pLibraryInfo`，link 后重查 stack、重算上界；link 前 host 核验各库 schema hash/interface hash（不符 → typed Err）；分库与单体两跑同场景同 SBT，输出逐像素比对（允许不等仅 stack 数值/handle——RFC F14 字面）。
   - FFI 追加：`vkGetRayTracingShaderGroupStackSizeKHR`/`vkCmdSetRayTracingPipelineStackSizeKHR` + library 相关字段。unsafe 全部归 **U30 扩注**（AS/SBT/device-address 细审计邻域，G3.6 先例 0 新 U 号）。
4. **harness `bin/vk_rt_incremental.rs`** + 固定场景：2 个三角形实例 → 2 个 triangles hit group（record 各含不同 material id + 颜色）、1 个 AABB 实例 → procedural group（intersection 报告 t + attr）、anyhit 腿（masked ignore 案例：anyhit 对特定 record 值 `ignore_intersection` → 该像素落 miss 色）、raygen 内 `execute_callable` 写 callable data 回读。单次运行产：hit-id 图（golden）、record readback SSBO（closesthit/anyhit/intersection/callable 各把自己的 record bytes 逐字节拷入 readback 区 → 与 packer 输入 memcmp）、stack evidence、library/单体两跑像素 diff。RED 注入开关：`--red-record-hash` / `--red-stack-undersize` / `--red-group-oob` / `--red-monolithic-tamper`。

## 6. M89 `g8.p0.m89.single_source_gfx_submit`（device 门）

### 6.1 实现方案（RD-037 三件套分解，backfill 字面①②③）

**① rurixc lowering：gfx pass 顶点供给面进 artifacts v2**

- artifacts v2 已支持全 stage_tag SPIR-V 入口表（RXS-0290~0292），vertex/fragment 真实体编码路已通（`dxil_spirv::emit_spirv_body_vulkan` + RXS-0301/0302 白名单，`vk_hw_raster_visbuffer_vs/fs` 为 accept 语料）——**本件的缺口只在 RHI 库面的顶点数据算子**。
- 语言面新增三个 builder 方法（`hir.rs` Op 追加 + typeck sig + `mir_build.rs` lowering，沿 `RhiRasterPass` 全套机械）：
  - `rhi.vertex_data(&VERTS)` → `Op::RhiVertexData` → `rxrt_rhi_vb_create(rhi, ptr, bytes, stride)`：`VERTS` 为 host 侧定长数组（`[f32; N]` 等），指针+长度传 cabi 拷贝；**stride 与顶点属性布局不由用户声明，由该 pass vertex shader 的 io 输入表推导**（P-11 单源：VS 输入 io 元素声明序 → 紧凑交错布局，location/format/offset 全部来自 reflection 同一提取律——`iface_extract::io_sig_for`）；
  - `rhi.index_data(&INDICES)` → `rxrt_rhi_ib_create`（首期 u32 index 冻结）；
  - `pass.draw_indexed(&vb, &ib, index_count)` / `pass.draw(&vb, vertex_count)` → `rxrt_rhi_gfx_draw(pass, vb, ib_or_0, count)`。
- `rxrt_rhi_raster_pass` 的 vs/fs 符号（GlobalAddr mangle 名）从"忽略"改为登记进 `GfxPassRecord`（cabi 侧按名索引 artifacts v2 入口表——`rxrt_ctx_create` 已解析 `spirv_entries`，同名匹配即得模块）。

**② cabi VB/IB 绑定符号**（追加式，`src/rurix-rt-cabi/src/lib.rs`）

- `rxrt_rhi_vb_create(r, ptr, bytes, stride) -> u64` / `rxrt_rhi_ib_create(r, ptr, bytes) -> u64` / `rxrt_rhi_gfx_draw(pass, vb, ib, count) -> i32`；句柄进 rhi 子表，`drop_rhi_children` 级联销毁（RXS-0194 口径，判据字面）；跨 rhi 误用/未知句柄 → 诊断 + RXRT_FAIL（既有 [structure] 体例，零新 RX 码）。装配核验追加：draw 的 `index_count*4 <= ib.bytes`、索引引用的最大顶点号 × stride `<= vb.bytes`（host 可核部分）——越界 draw 在 submit 前拒（RFC §4.2 字面）。

**③ `rxrt_rhi_submit` gfx 派发臂**（阶段 2 Vk 分支）

- `rhi_submit_vk` 内：gfx pass 若绑定了 draw + vs/fs 符号 → 组 `RhiGfxRasterPassV2`（既有 `RhiGfxRasterPass` 加 `indices: Option<&[u8]>` + `index_count`，或新 struct 加性并存）→ 调 vk.rs 扩展入口 `run_rhi_graphics_offscreen_v2`（在 U31 边界内加 IB 绑定 + `vkCmdBindIndexBuffer` + `vkCmdDrawIndexed`；barrier plan 逐字重放不变）→ 输出写回 `vk_resources` host 镜像 → 既有 `rxrt_rhi_readback` Vk 分流直接消费（零改动）。未绑 draw 的 gfx pass 维持"仅参 barrier 推导"（既有语料 0 回归）。
- **seal 双向核验扩面**（rhi.rs）：pass 声明集 ↔ shader reflection 资源集精确相等已有骨架；追加 VS io 输入表 ↔ VB stride/attrs 一致、FS 输出 ↔ color target 在位（artifact/reflection/VB range mismatch RED——RFC §5 RP-GFX-SUBMIT 锚定计划字面）。

**零 Rust 宿主判据的落地**：fixture `conformance/gfx_submit/accept/m89_two_tri_quad.rx`——两个直角三角形拼满屏 quad（共享对角线，top-left 规则下覆盖完备且确定），VS 传递 `#[interpolate(flat)]` 颜色，FS 输出 flat 色（全程 RXS-0301/0302 白名单内、整数域像素——Q-PixelCriterion 先例不设容差）；`.rx` main 内 `rhi.readback` 后自断言角点像素并以退出码报告；启动链 = `rx build m89_two_tri_quad.rx` → EXE（通用链，非 workload 专用）。**golden 比对通路**：cabi readback 增通用 env 开关 `RURIX_RHI_READBACK_DUMP=<path>`（运行时通用特性，非 workload `.rs`）→ smoke 比对 dump 文件与 checked-in `tests/gfx/m89_golden.rgba8` 逐字节。`rust_host_source_count == 0` 审计腿：fixture 目录与启动链零 `.rs`、cabi/rt 无 fixture 名硬编码（静态审计）。

M32系列预留3~4枚码，具体数量以实测为准，设计文档中会给出建议和备选方案。对于M50目标零新码的部分，我在评估是否能将record位置违例、schema错配、非法组合等都归入现有码（RX3012、RX3013、RX3017），其中RX3017作为RT入口标注契约违例的family比较合理。

对于callable index越界或非常量的情况，可以扩RX3012来处理调用点契约；动态SBT实参则需要修订RXS-0245的判据，trace_ray签名违例目前归RX3013扩类别。设计思路是逐项映射到现有码，只有在语义差异太大时（如hit_group声明违例）才考虑新增RX3024。M89同样目标零新码，draw/VB/IB装配违例通过库层的状态值处理，编译期builder方法签名违例走既有typeck机制。

M30/M85也是零新码，库层用typed Err加CLI非零退出和诊断文本。现在看着几个预算计数器来追踪shader排列、能力配置、PSO缓存、shader清单阶段和RT管道增量特性的见证数，同时标记了规范文档中的热点区域来避免并行冲突。

接下来需要检查多个源文件中的不同模块区段——rendering_platform、shader_stages、vulkan_backend、rhi、reflection、driver和vk等——其中M50和M89在mir_build中有不同的操作，一个处理RT根收集，另一个处理draw操作降低，虽然冲突风险低但需要小心处理append型的修改。

对于治理热点文件如number_ledger.json、预算评估脚本和CI门控配置，策略是在每次rebase后按实测的next_free值串行填号并重新生成追踪矩阵，避免并行分支各自预填。建议按host shader platform轨道分组Agent，其中M29到M32再到M85需要串行处理，因为它们共享多个关键文件。 现在我在梳理合并顺序的依赖关系——A(M29)→A(M32)→D(M30)→A(M85)→B(M50)→C(M89),其中C可以在D之前进行,因为M89和M30没有相互依赖,只有M29/M32到M85的manifest键依赖和M30到M85的PSO键依赖是硬约束,而M50和M89与M85之间没有依赖关系。各模块的工作量分别是M29=M、M32=M、M30=M~L、M85=S~M、M50=XL、M89=L。

每个PR都需要运行check_g8_implementation_interlock --require-ready作为前置检查,我准备写一份详细但易扫描的文档,大约600-900行markdown,用表格列出检查清单和RXS计划。对于M29的规范键,我需要强调"规范键两次生成逐字节相等"和"合法组合集合与golden集合全等"这两个判据,同时指出M31的pipeline_key前像已经包含variant_key和permutation_domain_digest,所以M29真值化后pipeline_key会自动按variant分裂。

对于M32的fallback分支设计,我在考虑低profile只生成允许的specialization,禁止能力对应指令/扩展计数为0的情况——提议用fixture对kmain(RayQuery)和kmain_fallback(SSBO),低profile禁止rt.ray_query所以选择fallback,生成的SPIR-V产物中不能包含OpRayQuery或SPV_KHR_ray_query相关指令;高profile则两个variant都可用,主variant优先选中。在"selection"层面,编译产物根据profile选择哪个entry作为逻辑入口的实现,设计上profile JSON的fallbacks映射逻辑入口到fallback入口,选中后artifacts v2入口表内该逻辑名绑定fallback模块。

现在我意识到两个entry都要编译成独立可寻址的variant,selection report指明低profile下逻辑入口到fallback的绑定关系,然后对选中的模块集合进行指令统计来验证禁止能力的判据,这样更严格地符合"只生成允许的specialization"的要求。

对于codegen的处理,低profile下如果entry的有效需求超出profile能力,就不发射该entry的主variant,只在编译产物中包含fallback;如果没有fallback映射就标记为错误。M32的验收条件是用--emit=check --profile high.json运行时产生0诊断,M50还需要扩展TLAS harness。

对于M50,我在考虑能否复用现有的VkAsManager来处理ray tracing pipeline的加速结构,而不是在rt_body里单独构建。关键是要遵循G7确立的单所有者原则——VkAsManager作为唯一的AS所有者,需要扩展它来支持instanceShaderBindingTableRecordOffset,而不是开辟第二套BVH/AS构建路径。

rt_body目前有自己的内联AS构建(来自U30时代,早于VkAsManager的W3设计),所以需要在最小改动和单所有者纪律之间做选择:要么在rt_body内扩展现有路径,要么迁移到VkAsManager统一管理。

新的run_rt_pipeline_offscreen会消费VkAsManager场景,保持旧入口不变,同时需要处理VK_KHR_pipeline_library扩展协商和接口创建信息,还要验证分库与单体的等价性。M89的golden测试用RGBA8格式的检入文件。

现在考虑GPU确定性风险:纯色三角形用最近邻着色应该能达到整数精确,但跨设备的像素级golden存在风险,特别是在三角形边缘;缓解方案是采样内部像素,使用轴对齐的几何体确保像素中心安全的边界。

最好的fixture是两个直角三角形沿对角线形成四边形,各自用不同的纯色填充——对角线边缘的像素覆盖在top-left规则下是确定性的。还需要在着色器中用flat插值修饰符处理顶点颜色,确保颜色在片段着色器中不被插值。

现在检查顶点着色器的直通和片段着色器的输出是否在允许列表内,这样图形管道编码路径就可用了——准备好写最终答案,包括关键设计决策的摘要段落、六个分段、以及执行顺序和并行分组。
