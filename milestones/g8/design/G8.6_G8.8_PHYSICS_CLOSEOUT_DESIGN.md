### 2.2 capture 容器与字节布局

目录式 fixture，三个文件（全部 LF、canonical JSON：固定字段序、浮点一律 8 位十六进制 bit pattern，保证 golden 字节稳定）：

**`header.json`**（`PhysicsCaptureHeader` v1，RFC §4.A1 全字段）：

```text
schema_id="rurix.physics.capture" · schema_version=1
jolt_version="5.3.0" · joltc_commit · joltc_abi_digest(=vendored Functions.h+Enums.h SHA-256)
rurix_build_fingerprint(rustc -V + workspace crate 版本) · platform="x86_64-pc-windows-msvc"
fixed_step_rational={num:1,den:60}（有理数，不存浮点）
world_desc(canonical) · id_domain_start
determinism_profile={job_threads:1, job_system:"ThreadPool",
  cross_platform_deterministic:false, double_precision:false, object_layer_bits:16}
budget_profile={contact_capacity, sync_budget 三轴}
recovery_layer="semantic_journal_rebuild_v1"   ← (c) 路线显式登记
scenario_id · tick_count
```

**`journal.jsonl`**（每 tick 一行）：

```text
{tick, pre:[命令…], post:{semantic_state_hash, event_digest,
  contacts_emitted, contacts_dropped, ring_backlog, saturation:{…}}}
命令类型 v1: create_bodies{descs+assigned_ids} | remove_bodies | apply_impulse
  | set_velocity | move_kinematic | page_resident/page_unload{page_key,receipt}
  | add_constraint{desc+id} | remove_constraint | set_motor{state,target}
  | (6b+ 追加: character_input / correction; 6c: apply_damage; 6d: vehicle_input/cloth_input)
```

**`state0.json` + `state_final.json`**：tick 0 与末 tick 的完整 `CanonicalPhysicsState`（诊断用；中间 tick 不存全量状态——定位器靠确定性重放重算，corpus 体积 ≈ 每场景数十 KB）。

**`CanonicalPhysicsState` v1 hash 前像（二进制布局）**：

```text
magic 'RXPS' u32 | version u16 | tick u64
| body_count u32 | 按 BodyId.bits 升序逐 body:
    body_id u64 | kind u8 | flags u8(bit0=is_active) | pad u16 | layer u32 | shape_id u64
    | pos u32×3 | rot u32×4 | linvel u32×3 | angvel u32×3   (全部 canonical bit pattern)
| constraint_count u32 | 按 ConstraintId 升序:
    id u64 | type u8 | enabled u8 | motor_state u16 | body_a u64 | body_b u64 | 参数 digest
| character_count u32=0 | destruction_count u32=0 | vehicle_count u32=0   (后波追加即 version bump)
```

浮点 canonical 化（RFC Q1）：`0x8000_0000 → 0x0000_0000`（−0 归一）；NaN（阶码全 1 且尾数非 0）→ capture/replay 即刻 fail-closed。`semantic_state_hash = SHA-256(前像)`，复用 `rurix-pkg::sha256`（M31 先例，零新依赖）。`event_digest` = 对该 tick 归一化接触序列（`events.rs` 既有规范序）逐条 `(a,b,phase,point,normal,impulse)` bit 编码后 SHA-256。**注意**：sleep 计时器等 Jolt 内部量不可经 C ABI 读取，不进白名单——hash 只含上表字段（F-12 白名单原则的落地边界）。

### 2.3 与"N=100 重跑"的判据区别（防假绿要点）

capture/replay ≠ 在测试进程里再跑一遍：capture 是**持久化版本化 artifact**，replayer 是**只读 artifact 的独立重建器**（不接触原场景构造代码），逐 tick 比 hash、逐条消费 journal（多余/遗漏/乱序/失效 generation 全 fail-closed）。smoke 的 RED 自检必须包含"篡改 journal 一条 → 红"与"删 journal 一条 → 红"。

### 2.5 divergence 定位器与故障注入

- 定位器：clean replay 与 injected replay 锁步推进，逐 tick 比 canonical 状态；clean replay 自身必须先匹配 capture hash 链（证明重放保真）；首个不等 tick 输出 `first_divergence_tick` + 逐字段 diff（字段路径 / stable ID / expected bits / actual bits）。
- 注入接口：`gate_runner inject --scenario S --tick T --body <stable-id> --field pos.x --bit N`。语义（F-12 冻结）：作用于**tick T 活世界 step 之前**，字段仅限 hash 白名单；写入走 `SetPositionAndRotation(DontActivate)`/`SetVelocity`，不附带激活副作用；白名单外字段 → 确定性拒绝。判据：全部注入 fixture 的 `first_divergence_tick == T` 精确成立（fixture 选定的 (tick,field) 组合在 corpus 建库时已验证可传播，避免被求解器吸收的误红）。

## 3. M67 `g8.p0.m67.network_physics` 设计（G8.6b，含 M71/M69）

### 3.1 架构裁决：`rurix-physics` 内新模块，不新增 crate

RFC §6.2 把 `network-physics`/`physics-character` 冻结为**库级 feature 名**，且网络层深度复用 capture 基建（journal 类型、canonical hash、replayer）——单 crate 内 feature 门控模块（`src/net/`、`src/character/`、`src/asset/`）避免跨 crate 暴露 capture 内部类型。模块划分：

```text
net/
  frame.rs       NetworkPhysicsFrameId newtype + FrameDomainMap 记录
  history.rs     有界 input/state/snapshot ring(容量冻结进 fixture;耗尽→显式 hard correction)
  server.rs      权威世界:逐 tick 应用全量输入,按节奏发 snapshot(语义状态+hash+schema/build digest)
  client.rs      预测世界:本地输入即时应用;收权威 snapshot→hash 比对→mismatch→rollback
  rollback.rs    恢复=journal 从 t0 重建至权威 tick(§1 (c) 路线)+重放[T+1..now]记录输入
  events.rs      PhysicsEventId 派生(类型+权威 tick+参与方 generation id 排序+tick 内 canonical ordinal)
                 + commit boundary(≤ server_confirmed_tick 才对外发布,恰好一次)
  smoothing.rs   仅作用 presentation transform 的 soft/hard snap;权威状态 0 影响
  trace.rs       NetTrace fixture 加载/校验
```

### 3.2 固定丢包/延迟 trace 的确定性模拟

**进程内双世界，零 socket**。`NetTrace` fixture（canonical JSON）：`{net_frame, inputs:{client_local, other_actors}, delivery:{snapshot_delay_ticks | drop}}`。误预测制造方式：trace 让服务端在 tick T 应用一条客户端不知道的 `other_actor` 输入（或丢弃客户端自己的输入），客户端预测轨迹随即偏离；golden physics-frame-id 处 snapshot 送达 → 客户端 hash 比对失败 → rollback/resim。双端同进程同二进制同画像，满足 F-13 的 hash 收敛适用条件并写入 evidence（`profile_match_recorded`）。

与 M66 复用关系：server 与 client 各挂一个 `CaptureRecorder`；rollback 的重建器就是 M66 `replayer`；rollback 起点、重放输入序列、最终 hash 全部落 evidence（RFC §4.B1）。

### 3.3 smoothing bound 两段式（RFC §6.5 程序，硬顺序）

### 3.4 M71/M69 范围裁决（G-G8-8B 原文要求的程度）

G-G8-8B 字面 = "M67 独立断言全绿；预测/权威修正/rollback-resimulation/事件去重/平滑全链；**CharacterVirtual 与 PhysicsAsset/ragdoll/physical animation authoring 闭环**"。后半句由波次 subject `g8.wave6b.m71.character_virtual`、`g8.wave6b.m69.physics_asset` 承载（RFC §6.4：不产 P0/P1 PASS、不入 8a 已 go P1 回归）。范围下限：

## 4. M68 `g8.p0.m68.fracture_pipeline` 设计（G8.6c）

### 4.1 cook 数据格式与 G8.3 复用裁决

`DestructionSourceAsset`（source）与 `DestructionCookedArtifact`（cooked）分离，共同头逐字复用 RFC §5.1 `SchemaHeader`。**复用 G8.3 的是"图式"不是代码依赖**：canonical 序列化纪律、source/cooked 分离、digest 覆盖（source+依赖+工具版本+cook profile）、未知版本 fail-closed 与 M79 双构建判据同构；cook 实现为 `rurix-physics::destruction::cook` 纯函数（fixture 规模无需接 DDC 服务；若 G8.3 落成的 DDC API 可直接挂，则 cook key 进 DDC——作为可选增强不作为门前置，避免跨波反向依赖）。

**cooked artifact v1**：

```text
chunks[]: chunk_id(stable) | 凸包/盒几何 | mass | interior/exterior face→material 映射
connection_graph[]: edge_id | chunk_a | chunk_b | strength | 有效接触面积
cluster_tree: 严格树(root→cluster→leaf chunk;非树 fail-closed) | 每层激活深度策略
anchors[]: chunk_id→world/static 锚
recipe 支持: ① 显式手工 chunk 分解(fixture 主力) ② 种子化轴对齐网格切分(盒) ③ 种子化 Voronoi(增强,确定性 RNG)
```

同输入独立双 cook 逐字节相等；悬空 edge/非树 cluster/非法 anchor/未知 schema 全 fail-closed。

### 4.2 运行时链

- damage 只经 journal 命令进入（`apply_damage{point,radius,magnitude,tick}`）——**注意在树子缺口：contact `impulse` 恒 0.0（VENDOR §3），strain 不得依赖求解器冲量**，v1 strain 源 = journal damage 命令 + 接触点相对速度（可查询量）；
- strain 求解：按 edge_id 升序确定性累积/传播，`strain > strength` → 该 tick 断键；连通性用 union-find（固定遍历序）重算，脱离分量按 cluster_tree 激活深度生成刚体（stable chunk/cluster ID → 派生 BodyId 进 journal，参与 capture 与后续网络 snapshot）；锚接分量保持 static；
- 阈值 fixture：阈下 N tick 零断键；阈上在指定 tick 断指定 edge 并激活指定层级 cluster（golden）；
- `DestructionCache`：逐 tick 记 command/event/state hash（无地址、无 Jolt 指针）；roundtrip = 序列化→重载→重驱动，事件序列与 semantic hash 逐字节不变；
- VFX 桥：仅消费 `FractureEvent{PhysicsEventId,tick,edge,chunks,cluster}`，按 `PhysicsEventId` 去重后向渲染侧事件队列恰好提交一次（host 可验证计数 + digest；rollback/cache 重放下仍恰好一次）。

### 4.3 checks.* 分解（12 项）

`cook_deterministic_double_byte_equal` · `cook_counts_and_digests_match_golden`（chunk/graph/interior-face/anchor 四类数量+digest） · `unknown_schema_fails_closed` · `dangling_edge_or_nontree_cluster_fails_closed` · `below_threshold_no_break` · `above_threshold_breaks_specified_edge_at_tick` · `cluster_activation_hierarchy_matches_golden` · `activated_bodies_enter_journal_and_capture` · `cache_roundtrip_event_sequence_identical` · `cache_roundtrip_state_hash_identical` · `vfx_exactly_once_per_fracture_event` · `vfx_no_duplicate_across_rollback_or_cache_replay`

## 5. M72 `g8.p1.m72.cloth_product_chain` + M70 载具设计（G8.6d）

### 5.1 ClothAsset schema 与 DCC 导入选型

- schema v1（canonical JSON + `SchemaHeader`）：panels（rest 拓扑：顶点/三角/uv，stable vertex ID）、seams（panel 边链缝合对）、fabric（stretch/shear/bend 刚度、密度、厚度）、collision proxies（胶囊/球集引用）、tether/bend/stretch 约束表（stable constraint ID）、LOD levels（降采样拓扑 + 跨 LOD 顶点映射数组）、sim↔render mesh/skin 映射、DCC/source digest、import recipe、schema version。
